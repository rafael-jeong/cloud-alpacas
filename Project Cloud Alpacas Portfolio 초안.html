Project Context

왜 이 프로젝트인가

Cloud Alpacas는 한화 이글스를 모델링한 가상의 프로야구 구단입니다. 저희 팀(Cellsforce)은 이 구단의 Fan Relationship Management 조직이 되어, Salesforce Customer 360을 실제 기업 프로젝트처럼 설계·구축했습니다. Phase 2에서는 팬 데이터를 활용해 새로운 스폰서·광고주를 발굴하는 B2B 확장이 시작됐고, 저는 이 흐름의 상품(Product)·견적(Quote)·캠페인 실행(Campaign) 영역을 전담했습니다.

이 프로젝트 전체가 지켜온 원칙은 하나였습니다 — Salesforce 기능을 먼저 떠올리지 않는 것.

Business→ Problem→ Persona→ Domain→ Salesforce→ Demo

아래 다섯 개 사례는 이 순서를 그대로 따라간 실제 작업입니다.

Case Studies

다섯 개의 실전 사례

Case 01

협상 가이드라인이 없다는 문제 — 정책을 데이터로 설계하다

고객 니즈 파악 → 솔루션 제안
문제
영업 담당자가 스폰서사와 가격 협상(Negotiation) 중 "얼마까지 할인해도 되는지" 기준이 전혀 없었습니다. 상품(Product)은 있었지만 협상 정책은 어디에도 없었습니다.
접근
Price Book / Price Book Entry 구조를 검토해, 표준 필드가 아닌 Max Discounted Price / Max Discount Percent 커스텀 필드를 제안했습니다. "왜 Price Book Entry인가"부터 팀에 설명하고, 13개 스폰서십 패키지 각각에 현실적인 할인 한도를 직접 산정해 입력했습니다.
결과
협상 테이블에서 담당자가 즉시 참조할 수 있는 정책 데이터 13건 완성.
고객이 말하지 않은 문제를 먼저 찾아 "이렇게 풀면 어떨까요"로 제안하는 과정 — Pre-Sales 컨설팅의 축소판입니다.
Case 02

AI로 견적 초안을 대신 만드는 Pre-Sales 어시스턴트

AI 툴 활용 · Pre-Sales 데모
문제
담당자가 Opportunity마다 스폰서십 패키지를 수동으로 고르고 견적 초안을 처음부터 작성했습니다.
접근
Agentforce로 Sponsorship Proposal Assistant를 설계했습니다. Opportunity 맥락을 읽어 적합한 패키지를 추천하고, 담당자가 확정하기 전까지는 실제 레코드를 만들지 않도록(Create 액션은 반드시 사용자 확인 후에만 실행) 설계했습니다.
검증
Setup의 Live Preview에서 실제 Org 데이터로 대화 흐름을 직접 시연·검증했습니다.
AI 도구를 실제 영업 워크플로우 안에 안전장치와 함께 붙이는 경험 — "AI 툴 활용"이 기능 자랑이 아니라 신뢰 설계의 문제라는 걸 배웠습니다.
Case 03

갱신 제안서를 위한 성과 요약 자동화

계약 후 고객 관계 관리 · 제안서 작성
문제
스폰서사와 재계약(갱신)을 논의할 때마다 담당자가 그동안의 실행 성과를 수작업으로 취합해야 했습니다.
접근
Before-Save Flow로 같은 스폰서사의 이전 시즌 캠페인들을 순회해 이행률을 계산하고, 연결된 Opportunity의 파트너 등급을 판정해 등급별 갱신 제안 문구를 자동 생성하도록 설계했습니다.
검증
실제 시나리오(2년 연속 협업 스폰서)로 이행률·등급 판정까지 end-to-end 검증했습니다.
담당자가 아니라 데이터가 갱신을 제안하게 만드는 구조 — Account 관리에서 "관계를 유지"하는 것과 "숫자로 설득"하는 것의 차이를 다뤘습니다.
Case 04

원인 불명의 플랫폼 버그 — 근본 원인을 좁혀가다

기술 트러블슈팅 · IT 솔루션 이해도
문제
Metadata API로 배포한 신규 커스텀 필드가 배포 성공 응답을 받고도 몇 시간째 화면·SOQL 어디서도 조회되지 않았습니다.
접근
Setup Audit Trail로 시점을 역추적하고, 같은 필드를 Setup UI로 직접 재생성하는 통제된 A/B 테스트를 설계해 "API 배포"와 "UI 생성"의 차이만 남기고 나머지 변수를 통제했습니다.
결과
Metadata API 배포 필드의 스키마 전파 지연이라는 재현 가능한 플랫폼 특이사항을 밝혀내고, 팀 전체가 쓸 수 있는 표준 우회 절차로 문서화했습니다.
"왜 안 되는지" 고객에게 애매하게 넘기지 않고, 직접 실험을 설계해 원인을 좁혀가는 과정 — Pre-Sales 상담에서 가장 자주 마주치는 상황입니다.
Case 05

병목 원인을 실시간으로 알리는 자동화

Pipeline 관리 · 팀 플랫폼 제약 해결
문제
캠페인 실행이 지연돼도 팀 리더는 레코드를 직접 열어보기 전까진 알 방법이 없었습니다.
접근
담당자가 이미 상황을 파악한 그 순간(상태를 "지연"으로 바꾸거나 마감일을 미루는 순간)에 자연스럽게 사유를 남기도록 6종 카테고리 필드와 검증 규칙을 설계하고, Slack으로 실시간 발송하는 자동화를 구축했습니다. 그 과정에서 Salesforce Flow의 비동기 실행 제약 3가지(비동기 경로 필수, 이전 값 비교 제한, 비동기 시점 재조회로 인한 데이터 stale 이슈)를 차례로 발견해, Before-Save/After-Save를 분리하는 구조로 해결했습니다.
검증
6개 지연 사유 전체와 예외 케이스까지 실 데이터로 발송·확인.
기능 하나를 완성하기까지 세 번 막히고 세 번 재설계했습니다 — 플랫폼의 제약을 이해하고 그 안에서 실용적인 답을 찾는 게 컨설팅의 실무라고 생각합니다.

Capabilities

이 프로젝트로 보여드리고 싶은 것

기능을 나열하기보다, 이 직무에서 실제로 쓰일 역량 단위로 정리했습니다.

고객 니즈 파악 & 솔루션 설계

  • 표준 기능만으로 해결 안 되는 지점을 찾아내는 것
  • 여러 대안을 비교하고 이유를 설명하는 것
  • Persona·Journey 기반으로 문제를 정의하는 것

Pre-Sales 데모 & 검증

  • Agentforce Live Preview로 실 데이터 시연
  • 멘토링 데모 시나리오·가이드 직접 작성
  • "확정 전 확인" 같은 안전장치를 설계에 반영

문서화 & 커뮤니케이션

  • Jira 스타일 Backlog, Crow's Foot ERD 작성
  • 의사결정 근거를 남기는 Decision Log 운영
  • 기술 발견을 팀 전체가 이해할 수 있게 정리

Salesforce 실무 구축

  • Record-Triggered / Before-Save / 비동기 Flow
  • Validation Rule, Custom Object·Field 설계
  • Slack 외부 연동, Agentforce 에이전트 설계

Closing Note

기능이 아니라, 문제를 풀고 싶습니다

이 프로젝트에서 가장 많이 반복한 질문은 "이게 왜 필요하지"였습니다. Salesforce를 잘 다루는 것과, Salesforce로 고객의 문제를 실제로 푸는 것은 다른 일이라는 걸 이 과정에서 배웠습니다. 비즈니스와 기술 사이에서 그 다리를 놓는 역할을 계속하고 싶습니다.
